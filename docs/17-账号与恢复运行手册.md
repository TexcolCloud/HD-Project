# 账号与恢复运行手册

更新：2026-11-13。以下入口服务于本项目的受控本机维护，不新增业务“超级管理员”角色。密钥、临时凭据、数据库备份及附件副本均保留在被忽略的环境文件或 `data/`，不上传仓库。

## 账号签发与找回

现有虚构演示账号保持兼容。新建学生档案时，服务器生成独立随机口令的摘要，标记首次改密，不返回或保存明文。账号维护人员核验学生身份后，通过下述工具重新签发24小时有效的随机临时凭据。没有共享默认密码，也不通过公开的“忘记密码”接口暴露账户资料。

```powershell
# 如尚未解析声明的Java依赖，先执行一次；不会接触真实库。
.\scripts\migrate-database.ps1 -SelfTest
.\scripts\account-maintenance.ps1 -SelfTest

# 先查询账号版本；每次变更都填写实际维护原因。
.\scripts\account-maintenance.ps1 -Action status -Username example-student
.\scripts\account-maintenance.ps1 -Action reset-password -Username example-student -ExpectedVersion 0 -Reason '身份核验后重新签发'

# 创建宿管并指定负责楼栋；初始凭据同样要求首次改密。
.\scripts\account-maintenance.ps1 -Action create-manager -Username example-manager -DisplayName '示例宿管' -BuildingIds '1,2' -Reason '核准新增值班账号'
.\scripts\account-maintenance.ps1 -Action set-buildings -Username example-manager -BuildingIds '1' -ExpectedVersion 0 -Reason '核准楼栋调整'
.\scripts\account-maintenance.ps1 -Action set-enabled -Username example-manager -Enabled false -ExpectedVersion 1 -Reason '人员离岗'
```

示例账号、楼栋ID和版本均需换成实际获批对象，不直接复制执行。`status` 返回账号ID、角色、状态、账号版本和首次改密标记，不返回口令。变更会拒绝旧版本，并追加维护审计。学生启停仍在学生档案中管理；宿管启停和范围变更在本机维护工具中处理。停用前应明确未结工单接续安排，停用本身不会擅自转移办理责任。

临时凭据只写入新的 `data/credentials/delivery-*.json`，文件使用POSIX 0600或Windows仅所有者ACL；拒绝覆盖已有文件及目录外路径。工具不在终端、审计或报告中打印口令。维护人员通过学校认可渠道交付本人，确认交付后删除交付文件。遗失、过期或交付失败时再次签发，而非查询旧口令。

临时账号登录后，后端只允许查询本人身份、安全凭证、改密和注销；其余业务接口返回 `PASSWORD_CHANGE_REQUIRED`。Web和鸿蒙引导到密码设置。改密要求至少10位、UTF-8不超过72字节且不得与旧密码相同；成功后临时标记清除，所有旧登录会话及其工作会话失效，使用新密码重新登录。

维护工具修改密码、宿管状态或楼栋范围时，同事务撤销登录、结束设备工作会话、清理最新位置及待学习片段，并使调度失效重算；历史工单、图片和进度不删除。当前登录限制为单服务进程内有界账号／来源摘要表，同一账号及来源5次失败后暂缓5分钟；服务重启会清空限制，不将其当作多实例网关防护。

## 配套备份与隔离恢复

SSH使用本机 `known_hosts` 严格校验，不能改成自动信任。所需传输包锁定在 `scripts/requirements-ops.txt`；已存在的 `.tools/ssh-python` 可直接复用。配置读取被忽略的 `deploy/.env.opengauss`，SSH管理凭据不传给Java应用。

```powershell
python scripts/opengauss-operations.py self-test
python scripts/opengauss-operations.py check --report output/acceptance/operations-health.json
python scripts/opengauss-operations.py backup --report output/acceptance/paired-backup.json

# 从刚生成的报告取得私有备份目录；每次恢复使用全新测试库名。
python scripts/opengauss-operations.py restore --backup-directory data/backups/<备份目录> --database dormlink_recovery_<唯一编号>_test --report output/acceptance/paired-restore.json
.\scripts\verify-recovery.ps1 -Database dormlink_recovery_<唯一编号>_test -Uploads D:/CodingProjects/HD-Project/data/recovery/dormlink_recovery_<唯一编号>_test/uploads
```

备份对全部当前业务表取得短时SHARE锁，允许读取，阻止写入；等待锁超时即失败，不解除业务外键或中断其他事务。锁内记录行数与工单／进度摘要，复制当前附件并核对大小，再生成 `gs_dump` 自定义归档；成功或异常都释放锁。应在低负载时执行，锁期间写请求会等待。私有目录包含数据库归档、附件、SHA256及配套清单，公开报告只含数量和摘要。未生成完整清单的失败目录不能用于恢复。

恢复只接受新的 `dormlink_recovery_*_test` 库和本项目独立 `data/recovery/`，拒绝主库、已有库、路径越界和摘要不符，不执行DROP或覆盖。恢复保留原项目角色的对象所有权，并仅为“指定库＋项目角色＋当前开发机/32”补充访问规则，保留其他拒绝规则。恢复后比对所有表行数、工单／进度摘要和附件元信息，逐文件读取SHA256，并撤销备份中的旧登录会话。`verify-recovery.ps1` 再以普通项目数据库账号读取工单，实际解码绑定的报修图片，避免仅超级用户能读取的假成功。

2026-11-12实跑结果：30表、23张工单、8条有效附件元信息及8份文件恢复一致；普通项目账号读取23工单，7张绑定报修图片实际解码成功。证据为 `closure-paired-backup.json`、`closure-paired-restore.json` 和 `closure-recovery-application-role.json`。早期容器用户组假设及恢复权限错误已修正，失败的隔离目标保留，不宣称这些尝试通过。

随后以最终应用JAR在独立8082端口启动同一恢复库及配套附件，禁止种子重建，自动应用V5／V6／V7。实际学生登录后读取历史已完成工单21及5条进度，并从受保护下载入口读取图片9（281,329字节），SHA256与配套原图一致，最后注销并停止该隔离实例。证据为 `closure-recovery-api.json`，其中记录最终包摘要、实际Java PID、迁移版本和停止结果；没有重启主8080或借用混合负载8081。

可复用 `scripts/verify-recovery-api.py` 完成同类HTTP读取核对，凭据只从进程环境 `RECOVERY_API_USERNAME`／`RECOVERY_API_PASSWORD` 读取，不接受密码命令行参数，不输出token。该工具明确拒绝8080及恢复目录外的预期图片。应选择获准查看的工单及其真实绑定图片，完成后删除进程临时凭据。

V1.3升级后的完整36表、8份附件文件另完成配套恢复及最终JAR HTTP读取验证，见`closure-v13-paired-restore.json`及`closure-v13-recovery-api.json`。11月13日界面终验结束后，又生成包含36表、25张工单、9条附件元信息和10份原图／缩略图文件的最新备份，见[最终备份](../output/acceptance/closure-final-paired-backup.json)；写锁已释放，健康检查通过。新备份包含整改验收、工单24／25确认、QA账号停用及测试位置清除后的事实，未对该新快照再次执行恢复；不能将前一次恢复结果误写成新快照恢复成功。

这是隔离恢复演练，未将主服务切换到恢复库。真正故障切换必须先停止旧实例写入，保存故障现场，再核对恢复库、附件目录和业务访问后切换配置，不能让两份数据库同时接收业务。恢复副本与备份含敏感信息，按学校策略设置保留周期并在确认后受控清理。

## 最小运行与故障处置

本机启动继续使用 `scripts/run-backend.ps1`，默认连接openGauss。固定 `FILE_STORAGE` 为持久目录，不能放入 `target/`；保留独立运行JAR及摘要，避免构建覆盖正在运行的Windows文件。生产环境模板见 `deploy/opengauss.service.example` 和 `deploy/backend.env.example`，只包含应用所需环境；模板尚未部署为真实生产服务。

正式使用关闭 `APP_SEED`，使用专用应用系统用户、受限环境文件、稳定附件磁盘和HTTPS反向代理，再启用 `COOKIE_SECURE=true`。证书与域名由实际部署环境配置；不为了验收生成信任全部证书或关闭认证的旁路。

`opengauss-operations.py check` 检查真实SQL连接、附件创建／读取／删除、64MiB磁盘余量门槛、消息待投递及失败数、调度dirty持续超过5分钟。结果失败退出码为2，便于现有监控或人工巡检接收，不把一次检查成功当作长期告警系统。

- 数据库不可达：先检查虚拟机、容器和网络，再检查受限HBA及项目账号；不重建主库、禁用鉴权或改用演示种子覆盖历史。
- 附件失败或空间不足：暂停受影响上传，保留元信息和原文件，恢复磁盘权限／空间后重试；不能通过删除业务附件释放空间。
- 消息失败或积压：检查接收账号状态、数据库及重试状态，修复后观察待投递下降；已读与业务完成分别处理。
- 调度长期dirty：检查应用日志中的异常类别、数据库连接及规划预算；恢复后确认新计划版本和待安排原因，不清空工单责任或冻结前缀。
- 进程异常退出：按部署服务重启策略恢复，先核对健康、数据库和持久附件，再恢复办理。多次失败停止盲目重启，保留日志和包摘要。

AI配置只从被忽略的环境文件加载，运行进程不会热读密钥。密钥轮换后重启本机后端并验证官方鉴权；不把密钥写入命令输出、客户端或报告。官方纯文本研判与反馈已完成接口及Web界面验证，结果见[16](16-服务闭环与联合验收.md)；官方附图研判和值班简报真实调用未计入通过范围。

当前真实容量、真机后台耗电与公网HTTPS均有各自条件，不能由本运行手册或隔离恢复结果替代其验收。
