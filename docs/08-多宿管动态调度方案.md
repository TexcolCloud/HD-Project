# 多宿管动态调度与任务路线

记录日期：2026年11月7日（Asia/Shanghai）。状态：已实现并完成本轮记录中的验收，Java同源运行包、最终HAP安装抽检与环境恢复均已完成。既有版本证据保留于[07历史基线](07-开发与验收.md)，本轮维护入口、实际证据层次和未测边界统一见[09动态调度交付与验收](09-动态调度交付与验收.md)。

## 目标与边界

用户补充要求：处理多笔报修时规划访问顺序；执行中有新工单时插入剩余流程；支持多位宿管，参与人数从登录活跃的宿管账号获取，不让操作者手填人数。

本功能称为“动态重规划”或“滚动调度”。它描述运行过程中更新计划的行为，不限定采用算法课中的动态规划（DP）。系统同时决定由谁办理、按什么顺序到访，并保留既有学生／宿管两种角色。

本轮已增加共享OpenAPI、Java调度与管理AI、Web任务调度页和原生鸿蒙路线模块，并保留独立验收记录。调度算法独立于数据库与UI，学生AI和宿管AI共用HTTP、配额、幂等与审计；新增能力由09的本轮证据支持，不沿用07结果扩大通过范围。

## 宿管人数与可用性

- 人员来源为有效登录会话中的活跃宿管，以用户ID去重；同一账号在Web、鸿蒙、多标签页登录均只算一人。学生不参与。
- V2已在auth_session增加last_seen_at，结合账号启用、会话到期／撤销和服务端时间判断活跃，不能把未过期会话数量当作在线人数。
- 当前参数为前台每30秒心跳、120秒内有心跳视为在线。跨端按账号去重；同账号一个会话退出，其他活跃会话仍可维持在线。
- 账号退出只撤销对应会话；其他有效会话仍在线时，该宿管保持在线。账户停用、会话过期与撤销即时影响资格。
- 在活跃人员基础上提供“接受新任务／暂停接单”。默认接受新任务；暂停后不新增任务，现有办理责任保留。此状态按账号共享，避免两端设置互相矛盾。
- 某笔工单的候选宿管，还必须拥有该楼栋权限，并有足够的可用工作时段。页面分别显示在线人数、参与人数和本单候选人数。

例如manager1负责A／B栋，manager2仅负责B栋；两人同时活跃时可分担B栋任务，A栋任务仍只允许manager1。系统需要候选人的身份与权限集合，不能只把数字“2”传给算法。

## 动态调整规则

| 发生事件 | 调度行为 |
| --- | --- |
| 新增普通工单 | 在有资格的宿管剩余路线中寻找增量成本较低的可行插入点；短时间内多笔新增合并计算 |
| 新增紧急工单 | 优先计算响应安排，提示受影响宿管；不自动中断其正在处理的事项 |
| 完成、取消、驳回、进入待确认 | 更新剩余任务；待学生确认的工单不继续作为上门维修站点 |
| 返修 | 明确需要再次上门后恢复为任务，默认保留原办理宿管；不能仅因重新规划就更换责任人 |
| 学生预约变更或处理超时 | 重算剩余到达时间；检查后续预约是否仍可满足，展示冲突 |
| 新宿管上线或恢复接单 | 可以分担未认领任务；已有承诺不因人数变化频繁转移 |
| 暂停接单、退出、心跳暂失 | 停止向该人新增任务；未接受的推荐任务可重新分配；已接单、在途与处理中的任务保留责任并提示跟进 |
| 确认无法继续办理 | 通过显式交接流程调整已接单但未开始的任务；保留原办理人、原因、时间与接收人记录 |

已完成任务不变；正在处理的任务固定在当前宿管。已经出发的下一站默认锁定，临时改变需通知并确认。优化对象主要是尚未出发的剩余任务。

短暂切后台或网络波动不得导致正在执行的任务被重复派给别人。系统离线时允许查看已缓存计划，但服务端重新确认前不能宣称新调度已生效。

## 位置、时段与工单责任

当前以楼栋／楼层粒度估算：同层1分钟、每层移动2分钟，A／B栋初始化双向5分钟；有双方楼栋权限的宿管可在Web维护通行链接。不以房号当距离，也不使用室内GPS；缺少跨楼通行连接时返回待安排原因。这些数值为可核对的估算，不代表校园真实测绘。

不要求室内GPS。宿管可以手选当前楼栋／楼层，以最近一次“到达现场”的任务作为已确认位置，保留确认时间；无位置时使用其选择的出发点，并明确显示这一假设。

“方便联系时段”自由文字继续保留，另有结构化windowStart/windowEnd。学生填写偏好，宿管才可确认硬预约；学生后续修改会使预约重新待确认。AI提取时间并写入安排不在本轮实现范围内。

当前预计处理时长默认30分钟，可由宿管调整；它参与时间窗和工作截止时间计算。按类别／历史自动校准属于后续改进，本轮不宣称已经实现。

路线上的推荐分配与“办理宿管”分别管理：

- 未接单工单可形成推荐任务，调度本身不跳过接单、开始、完工、学生确认等状态。
- 宿管接受推荐任务时，事务内校验最新工单版本与楼栋权限，再确定唯一办理责任；不能产生两位宿管同时接同一工单。
- 已接单工单默认只在原办理宿管的路线内排序，跨人变更走明确交接。
- 未完成但等待配件、等待学生或无需上门的事项不强塞进当前上门路线，保留待安排原因。

## 算法实现与扩展边界

先检查硬约束：楼栋权限、唯一办理责任、已锁定站点、已确认预约、可用工作时段与位置连通性。无可行解时，工单留在“待安排”列表并说明原因；不静默丢弃，也不假造在线人员。

当前RoutePlanner采用多宿管可行插入与有界局部优化，不依赖模型、网络或数据库：

1. 获取活跃人员、剩余路线、工单与版本的一致快照。
2. 固定已执行部分和当前站点，为有资格的宿管分别枚举新任务插入位置。
3. 将原有任务的服务时长与新增路程一并纳入计算，向后推算到达时间；不能只看插入点前后两段距离。
4. 排除违反硬约束的候选，按紧急程度／等待时间、额外通行与等待成本、预计剩余工作时长及改动幅度选择方案。
5. 仅改善未锁定后缀并进行受限跨路线移动；已认领任务不能因负载变化转给其他人，每次移动重新验证约束。
6. 新宿管上线或恢复可用后，可以分担既有路线中尚未认领且没有硬预约的任务；保持冻结前缀和已有办理责任。该新增回归的最终全套结果见09。
7. 未来时间窗急单之前的等待空档可以插入可行普通任务；重新计算急单到访，以实际迟到而非等待窗口本身施加优先级成本，保留冻结前缀及预约约束。相关回归验证普通任务先做且急单不延误。
8. 返回预计通行、等待与最大工作负载等指标；对提交顺序基线不可行的样例不伪造节省率，不声称全局最优。

负载使用预计剩余工作时长衡量，不用工单数量直接均分。一笔长任务可能比数笔短任务更占时间。对长期未安排工单提高关注程度，避免新任务持续挤压旧任务。

当前以保留可行旧后缀、冻结执行前缀和受限移动控制计划改动；评分权重是项目启发式。实际校园执行偏差、通知成本与权重校准尚无现场测量，不宣称获得最优权重。

每次普通新增优先做增量插入，显著延误、人员明确离岗或多个未安排任务积压时再扩大重规划范围。多人、紧时间窗或更大批量使简单插入质量不足时，可替换为Java OR-Tools等求解器，沿用相同输入、约束与验证器。

## 状态保存与并发

复用Java单体、MySQL和现有鉴权；第一版不额外引入消息中间件、Redis或独立优化服务。

V2迁移已经增加会话心跳、结构化上门窗口及dispatch_manager、dispatch_task、dispatch_revision、dispatch_plan、dispatch_event、dispatch_travel。SchemaMigrations记录校验和，升级保留旧业务；已应用V2不能原地改写，应新增迁移。

DispatchSignals在业务提交后合并dirty信号；Coordinator每秒检查并在事务外计算快照。Repository发布时锁revision，重新核验工单、人员资格和通行配置指纹；冲突最多重试3次，仍冲突保留dirty等待下一轮。启动强制重规划，避免进程中断后继续使用旧计划。

同一工单只能有一个当前有效任务占用，需由数据库约束与事务保证；提交重试须幂等。计划变更保留前后顺序、触发事件、估算变化及影响人员，不覆盖既往记录。

事件短暂合并，处理期间新事件保留后续重算；当前由定时协调器检查dirty，没有引入实时推送服务。Web与鸿蒙读取新版本后显示新增与调整站点，不允许旧响应覆盖新计划；多实例部署再增加协调机制。

## 三端呈现

Web已有独立“任务调度”页：在线／参与人数、接单开关、本人位置和可用截止时间、授权范围的路线／待安排原因、认领与执行、通行配置及显式交接。每位宿管仍受楼栋范围限制，不增加隐含超级管理员。

鸿蒙已有独立“本次路线”、设置、任务卡和前后台心跳模块，支持认领、出发、到达、受阻、恢复和刷新。显式跨人交接本轮仅在Web开放，不能宣称原生端已有交接入口。维修结果继续由原工单详情填写；到达不等于开始或完成维修。API24的PATCH由已有RCP组件发送，不要求升级SDK。

学生端已有可上门偏好及确认状态，未实现面向学生的路线ETA推送或到访通知；估算与已确认预约保持区分。

宿管AI提供主动调用的单单研判和文字值班简报，显示服务端事实、授权工单引用与待核查建议；不自动填写处理时长、变更路线、转派、修改预约或流转工单。单单研判附前3张图须另选，默认不附图；简报无附图。调用由AiGateway与AiRequestLedger共用配额、审计及短事务幂等，事实和建议作为同次结果冻结，具体失败重放语义见03和09。

## 本轮终验清单

真实MySQL调度HTTP7组已通过，Web与原生本轮关键场景已执行；精确步骤、环境和未测分支仅在09记录。下列保留为标准，不能据此扩大为所有设备／所有分支均通过。

1. 两个真实宿管账号在线产生两条人员路线；同账号Web／鸿蒙同时在线不重复计数，学生不计入。
2. manager2仅B栋，无论距离、在线人数与负载怎样变化都不能获配A栋工单。
3. 执行中新增工单，插入可行后缀；已完成、当前处理与锁定下一站保持不变。
4. 新工单造成已确认预约冲突时，返回待安排原因；紧急任务不会静默挤掉预约。
5. 多端同时接单、调度同时计算与取消、旧计划迟到等场景，不重复分配、不回退状态。
6. 一端退出、另一端仍在线；短暂断网后恢复；全部宿管离线时，人数与任务归属均正确，未安排任务可追踪。
7. 同一组任务与相同约束下，对比提交时间顺序和优化方案，报告预计通行时间、等待时间、跨楼次数、最大个人负载、重分配次数；允许算法在某些样例没有收益，不伪造节省率。
8. Web应用内浏览器与鸿蒙模拟器联合操作：一端新建任务，另一端收到新版本并现场执行；复测现有报修状态闭环。
