# P3C规范与重构质量门禁

日期：2026-11-11。用户已确认“阿里的规定”指阿里巴巴 Java 开发手册／P3C。本文件是拟采用的规则与门禁方案；本轮没有安装P3C插件、改格式、配置CI或执行完整自动合规扫描。扫描证据见[p3c-project-scan.json](../output/analysis/p3c-project-scan.json)。

## 1. 规范来源和适用性

规范依据锁定为 [Alibaba官方P3C仓库](https://github.com/alibaba/p3c/tree/6c59c8c36ecd8722c712d5685b8c3822c1c8b030) 当前核对快照 `6c59c8c36ecd8722c712d5685b8c3822c1c8b030`，含黄山版手册；实施时记录所用PDF的版本和校验和。逐条映射“手册条款、强制／推荐、项目是否适用、自动规则或人工检查、例外原因”。不可把内部风格偏好冒充阿里强制规定。

官方工具 `p3c-pmd 2.1.1` 依赖 PMD `6.15.0`，官方说明仅实现54条规则，不覆盖手册全文。项目使用Java21、record和现代语法，不能直接使用历史引擎并把解析失败当零问题。[官方依赖](https://github.com/alibaba/p3c/blob/6c59c8c36ecd8722c712d5685b8c3822c1c8b030/p3c-pmd/pom.xml)、[工具范围](https://github.com/alibaba/p3c/blob/6c59c8c36ecd8722c712d5685b8c3822c1c8b030/p3c-pmd/README.md)。

可评估支持Java21的PMD7，候选稳定版为 [7.29.0](https://github.com/pmd/pmd/releases/tag/pmd_releases%2F7.29.0)。旧P3C自定义规则依赖的AST／XPath／API需要迁移或人工映射，不能只强行替换PMD依赖。先用record、文本块、模式匹配及每条规则的正反例验证兼容，再决定锁定版本。[PMD7迁移说明](https://pmd.github.io/pmd/pmd_userdocs_migrating_to_pmd7.html)。

## 2. 当前可确定的差距

- Java采用两空格缩进，而所选阿里格式条款为四空格；`Db.java:38`等存在非空单行if无大括号。默认Google Java Format不能直接证明P3C合规，可评估四空格模式，但仍需独立大括号／命名检查。[官方格式规范](https://github.com/alibaba/p3c/blob/6c59c8c36ecd8722c712d5685b8c3822c1c8b030/p3c-gitbook/编程规约/代码格式.md)、[NeedBraceRule](https://github.com/alibaba/p3c/blob/6c59c8c36ecd8722c712d5685b8c3822c1c8b030/p3c-pmd/src/main/resources/rulesets/java/ali-flowcontrol.xml)。
- 当前pom未声明P3C／PMD／Checkstyle门禁，本地未见 `.github` 工作流。此观察不代表远端不存在分支保护，本轮未核查远端设置。
- Web多处长物理行使评审困难；原生Index职责集中。这些属于项目跨端工程约定，阿里Java手册不直接约束Vue／CSS／ArkTS。
- 契约重生成、规则报告和测试报告尚无完整统一门禁。行为测试通过不能替代规范、权限与性能审查。

## 3. 项目规则矩阵

| 类别 | 重构执行标准 | 检查方式 |
| --- | --- | --- |
| 格式和命名 | 四空格、控制结构大括号、清晰语义命名；单独格式提交，不混入行为变化 | Java21兼容格式器与规则映射；人工评审 |
| 分层和数据类型 | Controller处理协议；用例控制事务／授权；SQL集中；公开输入和规划核心类型化 | 工程约定及契约／行为测试，不伪称所有类必须接口+Impl |
| 异常与日志 | 不吞失败、不用成功响应掩盖异常；保持错误码；参数化日志，敏感字段不输出 | 适用P3C规则、故障注入、日志审查 |
| 并发和资源 | 生命周期可停止；线程／队列／图片处理有界；锁和事务持有时间可观察 | 人工语义评审、竞争与压力测试 |
| 数据库 | 参数化查询、范围过滤、必要字段、分页和聚合；索引经计划验证；保留关键约束 | openGauss集成、SQL计数、代表数据EXPLAIN |
| 数字与单位 | ID外部字符串；位置／速度／时间单位明确；空值与0、未知与静止分开 | 类型与单位测试；不为传感器数值机械套用金额BigDecimal规则 |
| 集合与性能 | 避免N+1和无界全量加载；已知规模才合理预分配，不盲目放大容器 | 代码审查和基线指标 |
| 权限与幂等 | 新请求和缓存重放都核对当前资格；数据库唯一与版本约束保留 | 越权／变更授权／重放／并发回归 |
| 注释和文档 | 解释不变量、单位、算法预算和真实限制；不堆重复注释 | 人工评审；对照实际契约与运行证据 |

阿里手册中的MySQL专属建议要做适用性判断。不能机械删除本项目关键外键、唯一占位或把PG BOOLEAN／BIGSERIAL改成MySQL字段。内部record、保留Spring JDBC和适当使用动态Map并不自动构成P3C违规。

## 4. 渐进门禁

1. 记录现有发现基线，包含规则ID、文件／定位、级别、解释和负责人；不直接给整个仓库一张“零违规”标签。
2. 新增和修改代码不引入新违规；解析失败、规则加载失败或扫描器崩溃直接失败，不能算通过。
3. 旧债按用例逐步消除；确需抑制时注明条款、原因与复查条件，不整包排除业务代码。
4. 生成模型、第三方许可和历史迁移设明确范围。Java格式器不改已应用SQL的校验和，客户端生成文件通过生成器维护，不手工修结果。
5. 工具只覆盖其实现的规则，事务、范围授权、资源生命周期、算法复杂度与定位数据用途保留人工检查。

建议实现阶段的检查链：

```text
Java21编译 + 格式差异 + 适用P3C规则
  → 契约DSL生成OpenAPI → TS/ArkTS重生成无漂移
  → 公开JSON字段和API1.1兼容测试
  → 纯计算／JDBC／真实openGauss业务与并发测试
  → Web与ArkTS编译及受影响测试
  → 性能预算比较 + IAB与DevEco／必要真机验收
```

远端配置留到实施并具备可审阅配置后再设置；不在本轮改变公开仓库权限或分支保护。Git分支、小批PR、单独格式／索引／行为提交是本项目拟采用的协作规则，不冒称阿里内部仓库制度。

## 5. 重构验收

- 先让针对缺失行为的测试失败，再实现；保留已有47项基线能力，并准确区分H2、纯算法与真实openGauss。
- 受影响接口保留API1.1字段、字符串ID、空值、错误码、幂等和版本语义；新设备接口先改契约维护源，旧客户端能忽略可选扩展。
- 不能把读取Java／ArkTS源码后替换字符串的测试作为新模块唯一保障；新计算模块提供稳定可调用接口，平台适配用SDK／设备验证。
- 无语义格式提交经行为回归后，再做逐用例重构；“文件少了”“行数短了”“新增缓存了”都不是性能通过证据。
- 性能报告记录硬件、VM资源、数据规模、请求分布、SQL／锁／连接池／堆／规划预算及前后结果，不能只提供一个平均响应时间。

本轮结论是**已有明确问题清单、规则依据与可执行门禁设计，尚未完成P3C自动合规认证或后端重构实施**。
