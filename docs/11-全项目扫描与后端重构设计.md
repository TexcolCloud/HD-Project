## 3. 保留的能力和不变量

- 保留 Spring Boot、Spring JDBC、openGauss PG 和原生 ArkUI，继续模块化单体。
- 保留纯 `RoutePlanner`、事务外计算／发布复核、冻结前缀、硬预约、唯一办理责任与不可行原因。
- 保留可撤销会话、Web CSRF、楼栋范围、本人的学生数据范围、附件鉴权及并发容量约束。
- 保留 AI HTTP 在事务外、完整幂等结果与授权事实，不将设备位置隐式发给模型。
- 保留三端共享契约、字符串 ID、ISO8601、空串与NULL区别、错误码、版本和既有幂等语义。
- 保留原生前后台生命周期、调度单飞／epoch与 RCP PATCH。新增设备生命周期在此基础上统一。
- 保留 R3 视觉基线。Web格式展开不改变用户界面、输入草稿或可访问性。

## 4. 目标结构

以业务归属组织包，包内按实际规模选择控制器、用例、SQL存取和类型；不要求每包固定四层，也不制造只有一个实现的 Service 接口／Impl。

```text
cn.dormlink
  identity/       会话、密码、当前身份与授权资格
  housing/        学生、宿舍与入住容量
  repairs/        工单、进度、访问安排与办理责任
  fieldservice/   访客、巡检；内部明确分开各自用例
  dispatch/       看板查询、计划协调、纯算法与受控执行
  mobility/       设备工作会话、观测准入、位置快照、通行估算
  media/          附件、图片处理与授权下载
  assistance/     供应商适配、AI账本、学生／宿管场景
  reporting/      授权统计查询
  shared/api/     少量稳定的分页、错误和传输约定
```

先处理行为与热路径，再移动文件；不得为了跨包编译把所有内部方法都变成 public。用例外部接口应小且明确，内部 JDBC 存取保持具体实现；只有确有硬件／回放、固定／学习模型等不同实现时才引入可替换接口。

请求 DTO 经显式校验进入用例；SQL 行在存取模块内部映射为类型；核心位置、质量、有效期与规划快照使用明确类型。动态 Map 可保留在真正动态的外部 JSON 和低层适配内部，不扩散成整个业务模型。Java DTO 的 JSON 字段、NULL及枚举通过契约测试固定，不能靠改类名隐式改线上字段。

### 看板与发布

看板读取不可变已发布投影；当前任务执行态、资格与权限的叠加必须来自一致性读取或明确版本复核。候选方案为短只读一致性事务读取投影和叠加数据，或存储完整版本投影；实现前用“读写交错”测试选定，不能在 READ COMMITTED 下随意拼接多次结果。

发布仍用短锁／条件更新验证输入版本。单实例可缓存不可变解码结果，缓存键至少区分计划版本；返回给用户前按当前授权过滤，授权缓存必须失效。精细坐标不进入所有宿管共用的响应缓存。

### 调度与设备数据

```mermaid
flowchart LR
  Device[设备观测与人工锚点] --> Mobility[会话与质量校验]
  Mobility --> Context[位置及移动估计]
  Context --> Travel[通行耗时估算]
  Travel --> Snapshot[不可变规划输入]
  Jobs[工单和预约变化] --> Snapshot
  Snapshot --> Planner[纯路线算法]
  Planner --> Publish[短事务复核发布]
  Publish --> View[授权看板与移动下一站]
```

传感器原始事件不直接调用算法。位置快照有独立 `contextVersion`，不能每次观测都增加人工接单设置的 `version`。实际锚点变化、可靠 ETA 明显变化、资格变化才请求重算；普通观测合并，急单／办理动作保持及时。任何预算耗尽都不能解冻在途任务或破坏已确认预约。回退旧计划前按当前完工／取消状态、归属、授权、资格与硬预约重新校验；无法确认当前仍可行时标记过期／待重算，禁止依据旧推荐认领执行，保留明确待安排原因。

## 5. 性能验证设计

本轮没有测量承诺值。实施时先固定机器、VM资源、数据分布、并发方式和版本，以独立测试库采集基线，再确定性能门槛。

| 观察指标 | 验证目标 |
| --- | --- |
| 每请求业务 SQL 次数、返回行数 | 看板和列表不随每个宿管／每条工单增加补查；用 SQL 计数验证，不以缩短 Java 文件证明优化 |
| HTTP p50／p95／p99、错误率 | 同数据同硬件前后比较；读优化不得提高冲突丢失或越权风险 |
| 连接池等待、事务时长、锁等待 | 看板读无全局排他行锁，图片 CPU 不占长事务；保留发布和认领的并发正确性 |
| 算法评估次数、耗时、预算耗尽次数 | 整个求解有预算；先改善初始插入／顺序罚分，再考虑并行或新算法 |
| 堆峰值、GC、图片并发数 | 图片与统计有可说明的资源上限；请求拒绝／降级可观察 |
| 观测接收／丢弃／合并、位置年龄、计划生成频率 | 位置频率与规划频率解耦，数据过时可见 |

代表组合建议：5／20／50名宿管，20／100／500个待办任务，普通／急单与硬预约混合；另准备1万／10万级历史工单、事件和附件元信息。定位按每设备10～15秒一个摘要批次建模：50设备约3.3～5请求／秒，原始传感器事件留本机。以上是负载设计，尚未运行，不能写为已支持规模。

查询索引候选包括 `repair_event(order_id,id)`、BOUND附件的业务组合、当前入住部分索引、会话用户／心跳、AI配额时间及按楼栋／学生排序的工单索引。先结合筛选、排序、授权、写放大和代表数据 EXPLAIN 判断，再新增迁移；不盲目把每个外键都加一遍索引。包含式LIKE和深OFFSET需要另评估查询体验及兼容方案。

新增需求先纳入设计，再指导重构。实现时可以先做设备适配器的独立探针，但不得先把高频数据接到现有全局锁和通用用户命令路径。每阶段的格式、行为、索引和设备能力变更分开提交；不把所有模块一次重写。

无需为本次目标预先引入微服务、Redis、消息队列、空间数据库插件或ORM。确有监测证据表明单体内有界方案不足时，再单独记录选择依据。
