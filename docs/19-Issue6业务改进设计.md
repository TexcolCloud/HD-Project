2026-11-18。本文记录 [Issue #6](https://github.com/TexcolCloud/HD-Project/issues/6) 七条业务反馈的设计和验收标准。实现以本地 `main` 的 `7b65709` 及既有工作区界面改进为基线。视觉沿用 R3 暖白／暖黑及 Web Lucide 图标体系。[界面规范](04-界面与设计规范.md) · [当前界面基线](18-界面收敛与交付版本.md)

## 访客超时与离访确认

超时以服务器查询时刻为准，条件为 `status == VISITING` 且 `now - arrivedAt > 24h`。跨午夜不足 24 小时和恰好 24 小时的记录继续显示「在访」。已登记离访的记录显示「已离访」。同一页用同一个 `now`，列表和详情在进入、页面恢复、手动刷新以及业务写入成功后重新读取。一直停留的页面以刷新后的结果为准。

在共享 `Visitor` 响应增加可选 `overdue` 字段，由已有 `OperationsService` 访客读取路径计算。旧接口响应缺少该字段时继续按原状态渲染，访客列表脱敏逻辑照常使用。查询时效以最新 GET 为准，幂等写入重放可能含有较早的快照。Web 复用危险色文本状态，ArkUI 复用 `palette().danger`，颜色旁始终显示完整状态文字。既有 12 小时服务消息继续提醒宿管核对实际离访。

Web 在列表及详情共用页面内原生对话框，鸿蒙复用应用内确认框。点击「登记离访」时显示访客姓名、房间和「确认后将按当前时间记录离访」提示，按钮为「返回」「确认离访」。取消、关闭确认框、离开页面或切换记录时不发请求。确认后再核对账号、页面、记录 ID 和版本，沿用 `POST /visitors/{id}/leave`、`expectedVersion` 与现有幂等机制。并发冲突后读取最新记录，请用户按实际情况重新确认。成功后列表和详情立即同步，迟到的详情请求不能恢复旧在访状态。

主要入口为 [Web 访客页](../web/src/pages/VisitorsPage.vue)、[鸿蒙访客控制器](../harmony/entry/src/main/ets/features/visitors/VisitorController.ets)、[鸿蒙访客视图](../harmony/entry/src/main/ets/features/visitors/VisitorWorkspace.ets) 和 [现场业务服务](../backend/src/main/java/cn/dormlink/fieldservice/OperationsService.java)。

## 学生端上门时间

继续用工单接口返回的 `windowStart`、`windowEnd`、`windowConfirmed`、`visitRequired` 和 `waitingReason`。列表短摘要与详情共用一套状态判断，详情时段用北京时间格式化。同一天可显示「11月19日 14:00–16:00」，跨日时分别标日期。宿管仍从工单的「上门安排」确认时段，学生从本人工单或「上门安排已更新」服务消息进入详情。详情进入和主动刷新复用现有查询生命周期。

| 判定顺序 | 学生看到的文案 |
| --- | --- |
| 待确认处理结果或已结束 | 「历史上门安排」，已有时段按实际记录展示 |
| `visitRequired=false` | 「暂不安排上门」，下方显示等待原因 |
| 没有有效起止 | 「暂未安排上门」 |
| 有起止、未确认 | 「可上门时段 · 待宿管确认」 |
| 已确认且时段已过 | 「预约时段已过 · 可查看最新安排」 |
| 已确认且时段有效 | 「已确认上门」及起止时间，当前已进入时间窗时仍显示完整区间 |

`estimatedMinutes` 表示预计维修时长，路线 `estimatedArrival` 是宿管侧规划估计，人工登记到场是独立事件。学生使用本人报修及服务消息权限。系统日历预约入口跟随当前有效确认状态。学生修改时段后回到待确认态，时段无改动时退出编辑并保留原确认。鸿蒙编辑入口对齐 `SUBMITTED / ACCEPTED / PROCESSING` 及原有办理宿管限制。返修继续读取工单中的预约字段，区块标题采用「工单记录的上门安排」。

主要入口为 [鸿蒙报修工作区](../harmony/entry/src/main/ets/features/repairs/RepairWorkspace.ets)、[访问安排](../harmony/entry/src/main/ets/features/visits/VisitArrangement.ets)、[日历提醒](../harmony/entry/src/main/ets/features/mobility/RepairReminders.ets)、[Web 宿管安排](../web/src/components/dispatch/RepairVisitPanel.vue) 和 [报修服务](../backend/src/main/java/cn/dormlink/repairs/RepairService.java)。

## 手机号与楼栋授权

手机号码按校内手机号场景拟定。访客登记、学生档案、报修联系号码在新建或改动时，去掉首尾空白后验证恰好 11 位 ASCII 数字。两端使用数字输入提示和「请输入11位手机号」的就地错误，粘贴超长号码时显示错误，避免截断后写入别人的号码。服务端以共享校验为准，返回明确的字段错误。掩码与号码数据库列保留现有表达。

三个写入场景均基于 `Inputs` 的共享规则，分别协调 `OperationsService`、`HousingService` 和 `RepairService`。访客若未更改号码可省略字段。学生档案更新须在授权、记录锁与版本核对后和数据库中的原号码比较，现有号码原样提交时允许更新其余字段。掩码文案留在展示层，表单提交使用有权编辑的原值或明确保留原值。若学校要接受座机、分机或境外号码，应在开发前选择兼容口径。此处的 11 位提案会收紧此前公开接受的写入范围，应在接口说明及发布说明写明，生成产物通过兼容脚本也要实测历史客户端。

学生与宿管账号新增独立的已验证登录手机号。注册激活、绑定换绑、登录、密码找回和人工恢复一并纳入交付，三端范围及验收见 [手机号绑定与账号恢复设计](20-手机号绑定与账号恢复设计.md)。

楼栋权限继续通过 `manager_building` 和 `BusinessSupport` 查询及写入校验。一人可负责多栋。登录后展示当前负责范围，默认可筛「全部负责楼栋」，只有多个负责楼栋时才需要单独选择。鸿蒙访客列表从有权限的 `/buildings` 获取选项，切换筛选回第一页并拒绝旧请求结果。学生池允许供入住使用的脱敏未入住学生查询，维持其现有用途。匹配楼栋时使用业务记录自己的楼栋快照，学生调宿后旧访客及工单仍归原记录楼栋。

授权变更复用账号工具的 `set-buildings`、预期版本、审计与会话撤销链路。现有新建楼栋时授予创建者该楼栋权限的规则继续适用。重新登录后应用新范围，开放工单按既有调度及异常接续规则处理。以仅负责 B 栋的宿管验证，能查询和办理 B 栋记录。A 栋记录的列表、详情、写操作、附件、供统计的聚合及调度候选均按现有授权规则过滤或拒绝。[账号维护](17-账号与恢复运行手册.md) · [共享授权代码](../backend/src/main/java/cn/dormlink/shared/application/BusinessSupport.java)

## 巡检日期和既有评分

Web 继续使用现有日期控件。鸿蒙用 API24 原生日期选择对话框，初始化为当前表单值，结束日期为北京时间今天，取消不动表单。确认后保存 `YYYY-MM-DD`，补录时提示选择或输入当日实际检查时刻，并按北京时间生成 `inspectedAt`。后端校验非未来、实际时刻与日期同日，这也关系到学生按入住区间查看的权限。

房间、日期和轮次选定后，先查 `/hygiene-inspections?roomId=…&inspectionDate=…&round=…&pageSize=1`。同一轮已有有效记录时展示日期、轮次、四项分数、总分及最近检查时刻，主操作为「更正评分」。同轮尚无记录时，可用同一列表接口按房间和 `endDate=所选日期前一天` 取一条最近有效巡检，显示来源日期与轮次。需要参考分数时主动点「带入四项分数」，只带入分项。本次检查时刻、问题、整改关联和照片按本次现场内容填写。可见范围与排序继续由服务端控制。切换房间、日期、轮次或账号时作废旧请求结果，填了一半的草稿应能恢复，切换业务目标前按现有规则确认。

| 现场动作 | 巡检写入规则 |
| --- | --- |
| 同次检查错填，需要更正 | 以该条记录初始化，提交 `PATCH /hygiene-inspections/{id}`，带原记录 ID 对应的 `expectedVersion` 和必填更正原因。默认保留检查时刻及房间。已有正式更正入口按现有规则允许调整日期／时刻 |
| 进行一次新的巡检 | `POST /hygiene-inspections` 建新记录。带入分数只是编辑便利，提交前仍核对本次真实评分 |
| 针对原检查重新检查 | 从「录入复查」进入，使用新 ID 与明确的 `relatedInspectionId`，同房间且检查时刻晚于原记录 |
| 另一位宿管已保存 | 接收版本或同轮唯一性冲突，提示刷新原记录并核对分项，保留本地输入，明确选择后才重新提交 |

使用现有评分校验和历史接口，四项各 0–25，合计低于 60 有问题说明。更正表单中已绑定的巡检图片只读，允许按既有上限补图。后端继续保护关联复查及整改验收所用记录，已参与验收的复查不能通过改分绕开规则。鸿蒙更正草稿需要携带写入意图、目标记录 ID、预期版本及当前账号上下文，未知提交结果继续使用同一请求键。日期选择、记录读取以及更正入口放在 `features/hygiene`，现场办理页继续复用已有控制器。[Web 卫生页](../web/src/pages/HygienePage.vue) · [鸿蒙卫生工作区](../harmony/entry/src/main/ets/features/hygiene/HygieneWorkspace.ets) · [鸿蒙巡检控制器](../harmony/entry/src/main/ets/features/hygiene/HygieneController.ets)

## 实施和验收

同次交付验收本页各项业务改进及手机号账号流程。访客 `overdue`、号码写入规则和账号接口先在 [契约生成器](../contracts/generate_openapi.py) 和 [接口说明](../contracts/API.md) 统一，再生成 Web 与鸿蒙模型。账号绑定及恢复使用增量迁移，其余业务改进复用既有结构。Web 保留当前布局，把信息放在原有状态位置，鸿蒙保留原生对话框和触控入口。

| 验收对象 | 可判定结果 |
| --- | --- |
| 超 24 小时 | 自动化用固定时刻覆盖 24h−1ms、恰好 24h、24h＋1ms、跨午夜及已离访。两端在日间和夜间都能读到同一超时状态，重新查询后消除旧状态 |
| 离访 | 取消时无网络写请求，确认后一条离访请求携带正确版本，重复点击不会重复写入。弹框期间换页、换账号或记录变更会中止旧意图。既有两宿管并发离访用例继续通过 |
| 上门时间 | 宿管确认，学生刷新列表／详情并从消息打开后看到同一时段。未确认、改期、暂不上门、过期、待确认处理结果等分支逐一核对，旧详情响应不能覆盖新确认 |
| 号码 | Java 和两端拒绝空、10 位、12 位及夹杂非数字的新增号码，11 位合法测试号码可提交。原样保留历史号码可编辑其他资料。失败提示不丢草稿，掩码和旧读接口仍可用 |
| 授权 | A/B 两个范围从列表、详情和实际写操作验证。改范围后的原会话失效，重新登录后列表和操作权限随之变化。验证未入住学生池的脱敏例外 |
| 巡检 | 日期选择、取消、未来日期和补录实际时刻在模拟器验证。已有四项分数预填，保存后同记录版本变化且历史含前后值。新复查生成新 ID，原记录可查，并发、越权、迟到结果及附件保留分别验证 |

Java 按 [P3C 映射质量门禁](13-P3C规范与重构质量门禁.md) 核对事务、权限、查询范围和格式。复用现有 `VisitorsPage.test.ts`、`RepairVisitPanel.test.ts`、鸿蒙 `workspace-reads`、`date-format`、`local-drafts` 回放，以及 openGauss 的 `PlatformIntegrationTest`、`ServiceFollowupIntegrationTest` 等测试表面。交付时执行契约兼容与生成一致性检查、三端构建和回归测试、真实 openGauss 集成、应用内浏览器 Web 自测及本机 DevEco API24 模拟器安装演练。此次文档记录的是实施条件与预期结果。
